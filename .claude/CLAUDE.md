# Part A — 프로젝트 고유 (매 프로젝트 작성)

## 프로젝트 개요

결혼 준비 전 과정을 한 곳에서 관리하는 **모바일 우선 반응형 웹앱**. 일정·체크리스트·비용·업체·하객·사진을 통합 관리하고 대시보드로 현황을 한눈에 본다. 커플(나+애인) 둘이 **로그인 없이** 클라우드 공용 저장소를 공유 코드로 함께 쓴다. 외부 배포 없이 **실제 내 결혼 준비 실사용**이 목적.

**핵심 차별점**: 모든 데이터(할일·지출·업체·일정·사진)에 '준비영역' 태그를 하나 붙여 **한 번만 저장**하고, 이를 영역별 뷰·전역 도구·대시보드로 자유롭게 재조합한다(하이브리드 정보구조). 한국 결혼준비 표준 체크리스트·로드맵을 시드로 미리 제공한다.

### 쓰기 — 정보가 생기거나 바뀌면

**사용자가 채팅으로 알려준 요구·제약·결정은 세션이 끝나면 사라진다.** 그 자리에서 기록하고 어디에 적었는지 보고한다. "나중에 정리"는 하지 않는다.

| 이런 정보 | 여기에 | 함께 갱신 |
|---|---|---|
| 만들 것·쓸 사람·**안 할 것**·성공 기준·용어 | `01` | 범위 변경 시 `04` 재편·**구조 영향 시 `02`+ADR** |
| 기술·라이브러리·구조·성능 예산 | `02` | **ADR 신규**(`02`엔 링크만)·예산은 `04`에도 |
| 저장할 데이터 형태·제약·스키마 | `03` | 마이그레이션 이력 + `04` 하위호환 테스트 |
| 만들 순서·완료 판정 기준 | `04` | — |
| **되돌리기 비싼 선택** | `decisions/` 신규 | 번복 시 새 ADR + 옛것에 `대체됨(→ADR-NNNN)` 표시 |
| 작업 결과 보고 | `reports/phase-N.md` 신규 | `04` 체크박스 + 이 파일 「진행 현황」 |
| 위 어디에도 안 맞음 | **적지 않는다** — `git log`가 갖고 있다 | |

**ADR 트리거**(그 자리에서 쓴다 — 나중에 몰아 쓰면 이유가 사라진다): ①되돌리기 비싼가 ②나중에 누가 "왜 이렇게 했지?" 물을 것인가. 미결정은 "추후 결정"이 아니라 `상태: 제안됨` ADR로 만든다. 양식·파일명·상태값은 `docs/decisions/README.md`.

**작성 게이트**(없으면 멈추고 먼저 채운다): Phase 0 착수 전 `01` 전체+`02` 시스템 컨텍스트·스택표, Phase 1 착수 전 `03` 초판+`02` 계층 구조, 각 Phase 착수 전 `04` 해당 Phase 검증 체크리스트, 되돌리기 비싼 결정을 내리는 순간 해당 ADR.

## 현재 상태

지금까지 된 것: 9개 화면 UI/UX 전부 승인(`design/*.html`, 「진행 현황」표 참고), 3단계 개발 진행 중 — Phase 0(기반)·Phase 1(홈·일정·체크리스트·비용 실구현) 완료, **Phase 2 중 하객·업체 관리 실구현 완료**(세부 체크리스트는 `04`). 갤러리·준비영역 모아보기·설정은 **화면만 승인, 실구현은 Phase 2~3**(`04` 참고). Realtime 2기기 교차 반영·하객 엑셀 가져오기/내보내기의 실기기 플로우·**업체의 실기기/웹 CRUD 실측**(마이그레이션 `0007` 미적용으로 보류)만 미검증(「알려진 이슈」). 세부·검증 내역은 **[phase-0](../docs/reports/phase-0.md)·[phase-1](../docs/reports/phase-1.md) 보고서**(얼림)가 단일 출처 — 구현된 화면은 보고서·코드가 최신 사실이고, 아래 요약은 그 둘과 어긋나면 진다.

**세부 기능 완성도 방침(사용자 결정 2026-11-02)**: 2단계 승인은 화면 구조·흐름까지만이고, 세부 기능(계산 로직·입력 폼·엣지 케이스)은 **3단계 실테스트 후 UI·기능을 함께 개선**한다 — 목업의 세부 동작을 과도하게 다듬지 않는다.

**화면별 핵심 구조**(`design/*.html` 기준 — 실구현 화면은 코드·보고서가 최신 사실):
- **홈** — 디자인 시스템 기준(baseline). 마스트헤드+D-day 센터피스(카드 없이 배경 위)+미니캘린더+바로가기 밴드+대시보드(흰 카드, 미터 2개 — 전체 진행·지출 진행률 — + 축의금 총액 금액 스탯 1줄[하객 구현 시 추가, 진행률 미터 아님, 지출과 상계 안 함]).
- **일정** — 캘린더↔리스트 세그먼트. 길일·D-day는 `couple.show_auspicious_days`/`wedding_date_status`로 게이팅. 준비 로드맵 위젯은 **사용 안함 보류**(2026-11-02, 사용자 결정) — 재배치하지 않는다, `system.css`의 `.roadmap`/`.rstep`은 삭제 않고 둔다.
- **체크리스트** — 영역별 섹션+진행률 미터. 완료 항목은 제자리에 체크+취소선(이동/숨김 없음).
- **비용** — 지출 단일 원장(ADR-0001). 업체별 기본견적+옵션→최종금액, 분담 정산(ADR-0004·[ADR-0005](../docs/decisions/0005-budget-progress-metric.md)).
- **업체 관리** — **실구현 완료, 실기기/웹 CRUD 실측은 미검증**(`app/vendors.tsx`+`features/vendors/`). **정보 관리 전용**(ADR-0001 — 금액 소스 아님). 영역 필터(체크리스트 `AreaFilter` 재사용)+계약 패널(영역당 여러 개 가능)+후보 리스트+폼 모달(후보→계약 전환은 모달의 명시적 "계약 확정"/"후보로 되돌리기" 버튼, 전용 토글 없음)+"비용에서 보기"(연결 지출로 비용 탭 이동 후 상세 모달 자동 오픈, `budget.tsx`가 `expenseId` 라우트 파라미터로 받음). 삭제는 연결 지출이 있으면 DB가 거부(PT409)하고 `Alert`로 사유를 보여준다. 쓰기 RPC는 `0007_vendor_writes.sql`(`create_vendor` 통합 확장+`update_vendor`+`delete_vendor` 신설) — **Supabase SQL Editor에서 아직 실행 안 함**, 실행 전에는 모든 쓰기가 실패한다.
- **하객 관리** — **실구현 완료·실기기 검증**(`app/guests.tsx`+`features/guests/`). 측 세그먼트+관계 다중필터 드롭다운(Set 기반, `budget/area-filter-dropdown.tsx`와 동일 패턴)+그룹 스위치(관계 enum 기준)+식대 단가 입력(couple.meal_price)+엑셀 가져오기/내보내기(SheetJS+Expo 공식 모듈, [ADR-0006](../docs/decisions/0006-excel-io-expo-modules.md), **파일 피커·공유 시트 실기기 플로우는 미검증**). 목업의 CSS `:has()` 트릭은 RN 상태 기반으로 재구현(옮기지 않음). 축의금은 지출 원장과 상계하지 않는 별도 수입 — 하객 화면+홈 대시보드 양쪽에 총액 노출, 측 세그먼트에 맞춰 대시보드 요약도 범위가 바뀐다.
- **갤러리** — 영역 필터+3열 썸네일 그리드(이미지 격자=카드그리드 금지의 예외).
- **준비영역 모아보기**(`areas.html`) — A(상세)+B(조망) 하이브리드 순수 CSS 아코디언. **더보기 메뉴에서 진입**, `more.html`(더보기 메뉴 자체)과 혼동 금지.
- **설정** — 결혼정보·공유코드·데이터·표시옵션. **톱니(`.gear-btn`)로 진입**, 더보기 메뉴엔 없음.
- **더보기 메뉴 허브**(`more.html`) — 서브화면 리스트(모아보기·업체·하객·갤러리).

**네비게이션 모델(사용자 결정 2026-11-03 하이브리드, 시안 비교는 [phase-2 보고서](../docs/reports/phase-2.md))**: 탭바 5개(홈·일정·체크·비용·더보기). "다가오는 일정" 전체보기는 **일정**으로, "할 일 추가"는 **체크리스트**로 간다(둘을 혼동해 버그였던 적이 있다).

**비주얼 방향(확정·변경 금지 — 사용자가 명시적으로 고름)**: 모던 웨딩 인비테이션(에디토리얼), 블러시/세이지 톤. seed reference `fe6a407796b1dfda`. `DESIGN.md` 전체가 규범 — 새 화면도 이를 상속하고 새 비주얼 월드를 고르지 않는다.

Phase 0·Phase 1 구현 세부(어떤 컴포넌트·마이그레이션으로 만들었나)는 위 보고서 두 건이 단일 출처다 — 여기 다시 적지 않는다. 구조 템플릿(`features/<도메인>/`)은 `02` 「디렉터리 구조」, 구현 함정은 `02` 「구현 함정」. 설계 스펙은 `docs/superpowers/specs/`.
- ⬜ 탭바 SVG 아이콘(현재 라벨 전용, `react-native-svg` 미도입) — Phase 1 폴리시로 이월.

새 화면을 만들거나 수정할 때: ① `design/system.css` 그대로 상속(새 토큰 추가 시 `DESIGN.md`도 갱신) ② 로컬 서버로 렌더 확인(「빌드 & 실행」) ③ `impeccable detect --json design/<file>.html` 0건 확인(실제 화면은 진짜로 고친다) ④ **사용자 승인 후에만** 반영 확정.

## 빌드 & 실행

**의도된 예외** — 코드에서 확인 가능하지만 매 세션 쓰이므로 여기 둔다. 어긋나면 코드가 사실이고, 스크립트가 바뀌면 여기도 고친다. 툴체인 근거는 `02`에 있다.

**화면 목업 뷰잉**: 빌드 도구 없음. `design/*.html`은 `design/system.css`를 링크하는 정적 파일. `file://`를 막는 환경에서는 로컬 정적 서버로 `design/`을 서빙 후 `http://127.0.0.1:PORT/파일명.html` 접속, 모바일 폭(390~430px)으로 확인한다.

**검증**: `.claude/skills/impeccable/scripts/impeccable detect --json design/<file>.html` 로 디자인 훅 검출 0건 확인. 결정 페이지 스케치(`.impeccable/mocks/decision/*.html`)는 fixture라 예외지만, `design/*.html`(실제 화면)은 발견되는 문제를 **진짜로 고친다**.

**3단계(개발) — Expo 프로젝트**(SDK 58, `src/app/` Expo Router): `npm install` → `npx expo start`(QR로 Expo Go/개발빌드 연결) → `npx expo-doctor`로 건전성 확인(scaffold 시 20/20 통과). 디자인 목업은 **참조용**으로 유지 — RN 구현 시 수치·레이아웃을 옮겨온다.

## 아키텍처 — 비자명한 부분

> 코드를 읽으면 아는 것은 쓰지 않는다. **읽어도 모르거나, 모르면 망가뜨릴** 것만 쓴다.

실제 함정 목록(RN 컴포넌트·Supabase 데이터 접근·비용 feature·화면 목업 CSS)은 **작업 영역별로만 필요해 매 세션 로드할 필요가 없다** — `docs/02-architecture.md`의 「구현 함정」 섹션에 모아 두고 해당 코드를 만지기 전에만 읽는다(「읽기」 표 참고). 새 함정을 발견하면 거기에 추가한다 — 이 파일에 쓰지 않는다. 다크모드 미지원(사용자 확정, 비주얼 방향 고정과 연동)만 예외로 여기 남긴다: 되살리려면 새 비주얼 월드 디자인이 필요해 「현재 상태」의 "비주얼 방향 변경 금지"에 바로 걸리기 때문이다.

## 알려진 이슈 / 기술 부채 [선택]

지금 "동작하지만 잘못된" 것들. 이걸 정상 동작으로 오해하지 않게 한다.

- **체크박스·스위치·드롭다운 체크의 터치 타겟이 24×24px 미만** — **체크리스트·비용·하객**은 실구현 시 `hitSlop`으로 해소됨(`CheckBox`·`Switch`·드롭다운 체크 전부 ≥24×24px 히트 영역, `docs/reports/phase-2.md`에 원 지적 상세). **업체·갤러리·모아보기·설정은 아직 정적 목업**이라 이 이슈가 남아 있다 — 실구현 시점에 동일하게 해소.
- **Realtime 두 기기 교차 반영 미검증**(사용자 확인 2026-11-11) — 브로드캐스트 채널 인프라(공유 코드별 격리)는 실측됐지만, 체크리스트·일정·비용·홈·**하객**(`trg_bc_guest`)·**업체**(`trg_bc_vendor`, 둘 다 0001에서 이미 연결)을 두 기기로 동시에 써서 한쪽 변경이 반대쪽에 반영되는지는 미확인. 두 사람이 함께 쓰기 시작하는 시점에 가장 먼저 확인(`docs/04-dev-plan.md` Phase 1 체크리스트·`docs/reports/phase-1.md`).
- **`CalendarView`가 외부에서 바뀐 `selectedDate`로 보이는 달을 재동기화하지 않음**: 지금은 `onSelectDate` 콜백으로만 날짜가 바뀌어 발동하지 않는다. 캘린더 밖에서 날짜를 점프시키는 기능이 생기면 `useEffect` 동기화가 필요하다.
- **하객 엑셀 가져오기/내보내기의 실기기 플로우 미검증**(사용자 확인 2026-11-12) — 순수 파싱(`guest-excel.ts`, 병리 입력 포함)은 단위테스트로 검증됐지만, `expo-document-picker`로 실제 파일을 고르고 `expo-sharing`으로 공유 시트를 여는 동작은 아직 실기기에서 확인된 적 없다.
- **뮤테이션 실패 시 RPC 미존재(마이그레이션 미적용)가 "저장했는데 사라짐"으로 보였던 사례**(2026-11-12, 하객 0006·비용 0005 INTERIM) — 체크리스트·일정·비용·하객·업체 5개 feature 모두 `onError`에서 롤백과 함께 `Alert`로 실패 사유를 띄우도록 고쳐 재발 시 바로 원인이 보인다. 새 마이그레이션을 추가하면 **Supabase SQL Editor에서 직접 실행**해야 한다(이 저장소는 CLI 링크 없음, `supabase/config.toml` 부재) — 코드만 커밋하고 끝내지 않는다.
- **업체 쓰기 RPC(`0007_vendor_writes.sql`) 미적용**(2026-11-12) — 코드·테스트(199개)·2단 서브에이전트 리뷰(스펙 일치+코드품질)까지 끝났지만 **Supabase SQL Editor에서 아직 실행하지 않았다**. 실행 전에는 업체 생성/수정/삭제·"비용에서 보기" 연동 전부 호출 즉시 실패(Alert로 사유 표시)한다. 실행 후 실기기/웹에서 후보→계약 전환·연결 지출 있는 업체 삭제 거부·"비용에서 보기" 딥링크(처음 시도되는 push 화면→탭 화면 라우트 파라미터 전달 패턴)를 실측해야 한다.

# Part B — 공통 규칙 (수정 없이 유지)

## 1. 소통 · 진행 방식

- **언어**: 모든 대화·보고·주석·커밋 메시지·문서는 한국어로 작성한다.
  단, 코드 식별자 · 외부 API 페이로드 문자열 · 기술 용어는 원문(영문) 유지.
- **자율 진행**: 작업 단위 완료 후 "다음 진행할까요?"로 멈추지 말고 계속 진행한다.
  단, **아래에 해당할 때만 멈추고 확인**한다:
  ① 삭제/덮어쓰기 등 **파괴적 행위** ② **무거운 환경 변경**(툴체인·런타임 설치, 저장 위치 변경)
  ③ **사용자 판단이 필요한 설계 분기**(라이브러리 버전 정책, UX 결정)
  ④ **명세와 크게 벗어나는 결정** — 여러 설계안 중 선택이 필요할 때
  ⑤ 요구사항이 **실제로 모호해 추측이 위험할 때** ⑥ **보안·권한·비용**에 영향을 주는 작업
- **완료 보고 형식**: 개발 내용 / 이슈 / 트러블슈팅 / 사이드 이펙트 및 조치 /
  검증 결과(+ **미검증으로 남은 것**) 5항목을 표·리스트로 요약한다.

## 2. 검증 · 완료 판정

- **추측 금지**: 버그·동작을 추측으로 진단하거나 "고쳐졌을 것"으로 완료 보고하지 않는다.
- **재현 우선**: 버그는 **재현 케이스(테스트)를 먼저 만들어** 원인을 눈으로 확인한 뒤 수정한다.
- **막힌 추측의 신호**: 같은 지점을 추측으로 두 번 이상 고쳤는데 증상이 그대로면 **가설이 틀렸다는
  신호**다. 더 고치지 말고 멈춰서 실측으로 진짜 원인을 찾는다 (원인은 대개 전혀 다른 곳에 있다).
- **경계 케이스**: 단일 케이스가 아니라 처음/중간/끝(경계값)·반복 동작을 직접 돌려 확인한 뒤에만
  완료 보고한다.
- **직접 실측**: 성능·동작은 실제 수치로 측정한다. 예산은 `02`의 「성능 예산」에 있고,
  **예산 대비 실측치**를 명시한다.
- **완료 정의**: "코드 작성" ≠ "완료".
  **테스트 통과 + 타입/린트 0에러 + 실제 재현 확인**까지가 완료다.
- **미검증은 미검증이라고 쓴다**: "됐을 것"으로 뭉뚱그리지 않고 **무엇까지 실측됐고 무엇이 남았는지**를
  분리해 명시한다.

### 시각 · 상호작용(UI) 검증 [선택]

- **실측 우회로 우선**: 헤드리스 환경이 시각 확인을 막으면 로직·수치는 **실측(DOM·좌표·크기)으로
  먼저 검증**하고, 육안 확인만 실제 실행 환경으로 넘긴다. 환경별 한계와 우회법은 기록해 재사용한다.
- **비동기 효과 측정**: 상태 변경 직후 동기 측정이 안 되면 **커밋을 기다린 뒤(await)** 측정한다.
- **임시 계측 코드 제거**: 측정용으로 주입한 DEV 전용 코드는 **검증 후 반드시 제거**한다.

## 3. 테스트 규칙

- **수정 = 회귀 테스트 동반**: 버그 수정 시 그 버그를 잡는 회귀 테스트를 반드시 추가한다.
- **오탐 없음 테스트 쌍**: "문제를 잡는 테스트"와 **"이미 올바른 입력은 건드리지 않는다"는
  오탐 방지 테스트**를 같이 작성한다.
- **병리 입력 테스트**: 빈 입력, 짝 안 맞는 구조, 공백/개행만, 깨진 형식 등 엣지·붕괴 케이스를
  별도 그룹으로 둔다.
- **불변식 테스트**: 멱등성(두 번 실행해도 동일), 보존성(개수·순서·내용 보존)을 명시적으로 검증한다.
- **하위 호환 테스트**: 저장 포맷·스키마를 바꾸면 **구버전 데이터를 읽는 테스트**를 함께 둔다.
  어디까지 읽어 줄지는 `03`의 「하위 호환 정책」에 있다.
- **커밋 전 필수**: 핵심 로직은 커밋 전 테스트 스위트 통과가 필수.

## 4. 설계 원칙

- **데이터-로직 분리**: "무엇인지"와 "어떻게 처리할지"를 별도 엔티티로 분리한다. 고정 규칙 N개로
  하드코딩하지 않고, 사용자가 설계·저장·전환할 수 있는 구조를 우선한다.
- **우선순위 기본값**: 하나의 대상이 여러 규칙에 매칭되면 **"구체적인 것이 일반적인 것을 이긴다"**.
- **프레임워크 비의존 코어**: 순수 로직 계층은 UI 프레임워크를 import하지 않는다.
- **방어적 파싱**: 정규식 단독 사용 금지. 상태 기반 토크나이저로 **무시 구간(주석/문자열)을 먼저
  마스킹**한 뒤 안전 영역에서만 정규식을 쓴다.
- **전부-아니면-전무(원자성)**: 여러 곳을 함께 바꾸는 작업은 실패 시 **전체 롤백**한다.
- **하드코딩 점검**: 완료 전 경로·네트워크·매직값을 훑고 **"의도된 고정값"**(문법 키워드·UI 문구)과
  **"환경 의존 하드코딩"**(절대경로·비밀키)을 구분해 보고한다. 후자는 즉시 외부 설정으로 뺀다.
- **재사용 우선**: 새로 만들기 전에 같은 일을 하는 기존 코드가 있는지 확인한다.

## 5. 코딩 컨벤션

- **타입 안정성**: strict 모드 필수.
- **네이밍 · 디렉토리**: 계층별 네이밍 규칙(예: 컴포넌트 PascalCase, 순수 로직 kebab-case)을 초기에 명문화하고, 새 파일 생성 전 정해진 트리와 맞는지 확인한다.
- **주석은 한국어로**: **언제 · 왜 · 어떻게 바꿨는지**를 코드 흐름 파악이 쉽도록 간결하게.

## 6. 문서 · 트리거 규칙

구체적 경로는 Part A 「설계·계획 문서」에 있다. 여기엔 원칙만 둔다.

- **문서 단일 출처**: 같은 사실을 두 곳에 적지 않는다. 한 곳에 적고 나머지는 링크한다.
- **코드가 사실이다**: 코드에서 확인 가능한 것(함수 시그니처, 디렉터리 목록, 빌드 스크립트)은
  문서에 쓰지 않는다. 문서와 코드가 어긋나면 코드가 이긴다.
- **이 파일에 이력을 쌓지 않는다**: 세션마다 통째로 읽히므로 지나간 기록은 비용만 늘린다. 무슨 일이 있었는지는 `git log`와 작업 보고서가 이미 갖고 있다. 작업이 끝나면 덧붙이지 말고 **바뀐 "지금의 사실"을 제자리에 반영**한다 — 코드 동작→「현재 상태」, 함정→「아키텍처」, 또 걸릴 것→「관례」, 잘못된 채 남은 것→「알려진 이슈」, Phase→「진행 현황」, 그 외 문서는 Part A 「쓰기」 표.
  **판단 기준**: "다음 세션이 이걸 모르면 잘못 작업하는가?" → 아니면 적지 않는다.
- **낡은 내용 제거**: 살아있는 문서를 갱신할 때 사실이 아닌 문장은 **지운다.** 덧붙이기만 하면 문서가 이력서가 된다 (얼린 문서는 예외 — 수정하지 않는다).
- **진행 상황 갱신**: Phase 완료 시점뿐 아니라 작업 도중 상태가 바뀔 때마다 갱신한다.

## 7. Git · 빌드 · 배포

- **커밋은 명시적 요청 시에만.** 별개 성격의 수정은 별도 커밋으로 나눈다.
- **커밋 전 절차**: status·diff·log 확인 → 메시지 작성 → 테스트·타입체크 통과 확인 후 커밋.
- **파괴적 git 명령 금지**: force push·`reset --hard` 등은 명시적 요청 없이 실행하지 않는다.
- **빌드 산출물 검증**: 빌드 후 **타임스탬프·크기를 실제로 확인**해 최신본인지 검증하고 보고한다.
- **배포 특이사항 문서화** [선택]: 코드서명 부재로 인한 SmartScreen 경고 등 최종 사용자가 마주칠
  문제와 우회법은 별도 문서(`DISTRIBUTION.md` 등)로 만들어 배포물과 함께 전달한다.
